## 一、结论摘要

1. 你报的两处卡顿不是同一个 bug，但属于同一类根因：**主线程在动画或切换的那一瞬间被同步工作占满**。
   - **切会话**：整段历史在同一帧里同步完成 markdown 解析 + KaTeX 排版 + DOM 构建；没有分片、没有虚拟化、没有图片懒解码，每条消息还挂一个入场上浮动画。
   - **开抽屉**：动画期间对一棵包含上万节点的卡片子树逐帧写**继承型 CSS 自定义属性**（触发整棵子树重算样式）并缩放它，同时遮罩的 backdrop-filter 每帧重算模糊。
2. 你的判断方向是对的：**主界面缩放确实是主要成本之一**，但成本不在 transform: scale() 本身（那是合成器操作），而在"被缩放的是谁"——一棵上万节点、并且由继承型自定义属性驱动的子树。毛玻璃是**叠加项**，不是主项；第 4.3 节给出"先不动视觉、按可测顺序逐项摘"的验证路径。
3. 实测（Node，桌面 CPU，只算解析，不含 React/DOM/排版）：一场 12 轮对话里 15 条中等长度带公式的回答，仅 markdown+KaTeX 解析就要 **约 102ms**，产出 **约 14,670 个元素**；如果回答偏长，是 **约 322ms / 58,680 个元素**。手机单核通常慢 3–5 倍，再叠上 React 元素创建、DOM 插入、KaTeX 字体排版与样式计算，量级正好落在 **0.5–2 秒的主线程阻塞**——这就是"非常卡顿"。

## 三、切到多轮会话：热点逐条

### 3.1 整段历史一次性同步渲染（主因）

- pages/Ask.jsx:67-68 取出 conversation.messages 与 visibleMessages(...)，:375-410 直接 messages.map(...) 全部消息。
- 每条消息是 MathMarkdown（Ask.jsx:400）→ components/MathMarkdown.jsx:13-15 的 MarkdownBlock 执行完整管线。MarkdownBlock 的 memo 只在**同一次挂载内**按 text 复用；**切会话是全新一棵树，memo 全部失效**，N 条消息 = N 次同步解析。
- 没有虚拟化、没有分片：.conversation-flow（styles/app.css:38）只有 overflow-y:auto，.message（:39）也没有 content-visibility。
- loadConversation 会一次取回该会话**全部**消息（core/db/engine.js:341-390），所以"整段历史"确实是整段。

### 3.2 每条消息的入场上浮动画

- styles/app.css:39：.message { ... animation: appear var(--motion-duration) var(--motion-ease); }，即 opacity + translateY 动画。切会话的瞬间，**N 条消息同时开始播这个动画**（只有 @media (prefers-reduced-motion: reduce) 下才会被关掉，tokens.css:75-81）。
- 这个动画对"新到达的一条消息"是合理的手感，对"整段历史同时出现"只是额外的合成与绘制负担。

### 3.3 图片消息直出 base64，无懒解码

- Ask.jsx:396-398：img 直接用 attachment.dataUrl，没有 loading=lazy、没有 decoding=async。
- engine.js:34 encodeImage 把图片在 Worker 里转成 base64 dataUrl 一并回传（engine.js:377-380 逐张内联进消息），于是切会话的那一帧会把历史里**所有图片同时解码**，并常驻为 base64 字符串。

### 3.4 消息里嵌套的练习卡：全量订阅 + 每卡一次串行 RPC

- components/ChatPracticeCard.jsx:12：const state = useChatPracticeStore() —— **订阅整个 store**，任意一张卡的数据变化都会让**所有**卡重渲染。
- :18：每张卡挂载即 state.load(itemId) → 一次 loadPracticeItem RPC；Worker 侧是**严格串行**队列（core/db/database.worker.js:25-31）。一场会话有 5 张卡，就是切会话时连续 5 次串行往返 + 5 次 store 广播。
- 每张卡内部还有 4–6 个 MathMarkdown（题干、各选项、反馈、解答，ChatPracticeCard.jsx:30,36,40,41,45）。

### 3.5 渲染完还要定位：滚动钩子每次滚动做 O(n) 强制布局

- app/useQuestionScroll.js:14-22：onScroll 里 querySelectorAll('[data-user-message-id]') + 对**每条用户消息**调一次 getBoundingClientRect()（:18），且**没有 rAF 节流**，每个滚动事件都要强制同步布局一次。会话越长、用户消息越多，滚动越重。
- Ask.jsx:78 每次渲染还会新建 userIds 数组并 join('|')（useQuestionScroll.js:12），这是 O(n) 的小成本，但发生在每次 render 上，可以顺手消掉。

## 四、开抽屉：热点逐条

### 4.1 --p 写在 .app-shell 上，是**继承型**自定义属性

- styles/app.css:20：@property --p { syntax:'<number>'; initial-value:0; inherits:true; }；:21 把 --p: 0 定义在 .app-shell 上。
- app/App.jsx:45-65 的 setDrawerProgress 在 rAF 补间里**逐帧** shell.style.setProperty('--p', ...)（:51、:53、:61）。
- 消费方三处：.base-card 的 transform: scale(...)（app.css:80）、.drawer-scrim 的 opacity（:87）、.history-drawer 的 translateX（:93）。
- 机制：继承型自定义属性每帧变化，Blink 需要让**整条子树**重新解析样式。这一条本项目上一次审查
  《性能与稳定性审查-2026-10-19》4.2 第 4 条已经指出过，但代码里仍然存在——因为当时优先修的是
  "内容撕裂 / 抬手闪现"两个确定性 Bug。子树里是整段会话的上万节点，所以这一项的成本与会话长度成正比。

### 4.2 被缩放的是整张 base-card（含上万节点，含输入框毛玻璃）

- .main-frame base-card（App.jsx:88）包住顶栏、三个区域页、整段会话与输入框。
- 缩放本身是合成器友好操作，但要让一张**包含上万节点、且未被提升为独立层**的卡片开始按帧变换，
  浏览器必须把它光栅化（raster）到一个可用图层上；app.css:77-79 那段注释其实已经记录了这个成本：
  "will-change / contain:paint 一旦常驻……切换会话时这个图层必须整体重新光栅化"。
  也就是说：**卡片越大，缩放这一步越贵**——这正是你的直觉所指的地方。
- 输入框 .composer 自带 backdrop-filter: blur(12px)（app.css:62），它位于这张会被缩放的卡片内部，
  整个动画期间需要跟着重新栅格化。

### 4.3 遮罩的 backdrop-filter 在落定动画期间没有关闭

- app.css:87：.drawer-scrim { ... backdrop-filter: blur(6px); opacity: var(--p); } —— 模糊半径固定、只让透明度跟随进度，写法本身是对的。
- app.css:88：.app-shell.is-drawer-dragging .drawer-scrim { backdrop-filter: none; } —— 只在**手指拖拽**期间关掉。
- 但"点一下菜单按钮打开抽屉"走的是 App.jsx:55-64 的 rAF 补间，dragging=false，**不会**加
  is-drawer-dragging，于是这 180ms 里：底层卡片正在缩放 → 遮罩的 backdrop 每帧都在变 →
  **每帧全屏重算一次模糊**。
- 结论：这是打开抽屉掉帧的**直接叠加项**，但不是唯一项，也不必然是最大项（见 4.1/4.2 两项与会话长度相关的成本）。

### 4.4 历史列表在"open 那一帧"才整体挂载

- app/HistoryDrawer.jsx:171-172：history-list 里是 {open && <>...}，即抽屉关闭时列表**完全不渲染**
  （:71-73 的分组也直接返回空数组）。
- 代价：点击 → open=true → 同一帧内 mount N 个 button（每个含一个 lucide 图标与两个 span）→ 布局 → 绘制，
  然后动画才起步。会话越多，"看到抽屉"的延迟越长，观感就是"点了没反应，然后一顿"。
- 注意这个取舍本身是对的（关闭时不渲染确实省开销），问题只在于"关闭时也不保留已渲染结果，每次都重新付一次"。

### 4.5 拖拽路径每帧强制布局 + 每次 touchstart 遍历祖先（既有遗留）

- app/useAreaSwipe.js:17：drawerWidth() 每次都读 .history-drawer 的 clientWidth；:22-27 peek() 在
  **每个 touchmove** 里调用它 → 每帧一次强制布局。宽度只需在 touchstart 缓存一次。
- core/ui/areaSwipe.js:28-35 的 blocksAreaSwipe 在每次 touchstart 向上遍历祖先并调 getComputedStyle，
  这是上一轮审查列为 L3 的遗留项，仍未修。它影响"开始一次手势的成本"，与本节其它项叠加在同一帧。

## 七、验证方法（供你自己测）

1. **构造一场长会话**：连续追问 12–15 轮带公式的数学题（长度接近你平时最长的会话），确认消息数在 30 条上下。
2. **桌面 Chrome**：DevTools → Performance，点 Record → 点历史项切到这个会话 → Stop。看 Main 轨道里
   Evaluate Script / Parse HTML / Recalculate Style 的**单帧最长块**与 Frames 轨道里的长帧。
   修复前后对比这个数字，比看体感稳定。
3. **手机**：Android 上用 chrome://inspect 连 WebView 同样录一次；或在 Android Studio 的 CPU Profiler 里
   看主线程是否有连续 200ms 以上的占用。
4. **抽屉**：在同一场长会话上反复"点菜单开抽屉 / 点遮罩关抽屉"，看 Frames 轨道是否出现长帧，
   并注意首次打开与第二次打开的差异（对应 4.4 的重复挂载成本）。
5. **底线**：任何改动都必须 frontend/tests 下 39 个 *.test.mjs（共 238 条断言）全绿，并且 npm run build 通过。
