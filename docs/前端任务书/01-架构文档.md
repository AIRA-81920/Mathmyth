## 1. 项目全貌（多维度解释）

### 1.1 一句话定义

**Mathmyth 不是"搜题 / 解题工具"，而是帮你把题目「归类、联网、避坑」的学习工具；解法只是副产品。**

它回答的不是"这道题怎么解"，而是：

> **"看到这种题，我该想到哪些解法？"** 以及 **"这一招，还能用在什么题上？"**

### 1.2 北极星（唯一目标）

> 培养**"解决问题的能力"**——看到一个问题，能**想出有哪些解法**。
>
> 注意后半句同样重要：**"这个解法能用到什么题上面"**。
> 所有功能都围绕这一件事，**任何不服务于它的功能都是多余的**。

### 1.3 使用者与使用场景

| 维度 | 结论 |
| --- | --- |
| 使用者 | **大一新生**，正在学高等数学（同济第七版，上册 + 下册） |
| 使用状态 | **边学边问**——知识体系还是一片空白，正在"搭建"，不是"复习加固" |
| 主形态 | **安卓 APK**（手机随身、随手拍） |
| 次形态 | 桌面 Electron（坐在电脑前时） |
| 人物设定 | **单人优先**——先自己用；但数据模型不把"单人"焊死，以后想给别人用不用重写 |

### 1.4 方法论原型：潘敬贞的「题根 + 变式探究」

这个产品的设计**不是凭空发明的**，它照搬一位真实教师的教学法：

- 背景：产品负责人的高三数学老师**潘敬贞**（广东佛山顺德容山中学）。
  该教学法有亲历实证——负责人高三一年数学年级排名从 600+ 提升到前 100，
  2026 年高考数学 101 分。
- 内核：**题根思想**（"题在考卷，根在课本"）+ **四把变式手柄**
  （数据变更 / 条件拓展 / 背景变换 / 结论应用）+ 一题多解 × 一题多变。

**关键定位差异（决定了产品形态）**：

| | 潘老师（"加固"） | Mathmyth（"构建"） |
| --- | --- | --- |
| 面对 | 高三复习，学生**已有知识体系** | 大一初学，知识体系**尚未搭起** |
| 主战场 | **变式题组**（练） | **问答**（构建） |
| 体系边界 | 有（高考考纲，能"深化到底"） | **没有**（学到哪算哪） |
| 错误性质 | "漏了" → 纠错 | "**这块还没搭起来**" → 补砖 |

由此推出三条**硬结论**：

1. **"题根"现在不合适**——"回归课本"对还没学完课本的人是空话（推到后期）。
2. **主战场是问答，不是练习**；练习与足迹是辅助。
3. **这棵树没有"终点"**——所以"只长用户碰过的"不是设计上的克制，
   而是**本来就不存在"应然的全貌"**。

### 1.5 核心结构：板块 → 情景组 → 情景 → 方法 →（点开）题目

只有中间两层是**能力单元**，其余是收纳与导航：

| 层 | 名称 | 是什么 | 举例 | 是能力单元吗 |
| --- | --- | --- | --- | --- |
| 1 | **板块** | 一"袋"相关东西的收纳盒 | 极限 / 导数与微分 / 不定积分 | ❌ 仅导航与聚合 |
| 2 | **情景组** | 板块下的分组（保证每层分支 ≤ 7） | 未定式极限 / 数列极限 | ❌ 仅导航 |
| 3 | **情景** | "**看到什么**"（识别单元） | 0/0 型、∞/∞ 型、0·∞ 型 | ✅ 认得出 |
| 4 | **方法** | "**想到什么**"（执行单元） | 等价无穷小替换、洛必达、泰勒 | ✅ 用得出 |
| 5 | **题目** | 挂在方法/情景下的具体题 | `lim(x→0) sin x/x` | ❌ 果实 |

> **UI 硬规则**：如果一个情景组下面只有 1 个情景，界面**自动跳过**这一层，直接显示那个情景。
> （来自 `skeleton/scenario_groups.json` 的 `ui_rule`）

### 1.6 这张网的核心：**边**

**可训练、可检验的最小知识，不是"情景"，也不是"方法"，而是「情景 → 方法」这条连线。**

因为一个"解法"单独存在时无法被使用——"齐次化"三个字回答不了"我什么时候该用它"。

整个软件做的事：**把"情景 × 方法"织成一张网，再检验用户能否自己顺着线走。**

示例（"求极限"板块）：

| 情景（看到什么） | 可用方法（想到什么，按优先级） |
| --- | --- |
| 0/0 型 | 等价无穷小替换 → 因式分解消零 → 洛必达 → 泰勒展开 |
| ∞/∞ 型 | 抓大头（同除最高次）→ 洛必达 → 因式分解消零 |
| 0·∞ 型 | 先化成 0/0 或 ∞/∞ 再处理 |
| ∞−∞ 型 | 通分 / 有理化 / 提取公因式 |
| 1^∞ / 0^0 / ∞^0 | 取对数；或用 lim(1+u)^(1/u)=e |

### 1.7 两个维度，分别挂在不同层（重要）

| 维度 | 含义 | 挂在哪层 | 判定方式 |
| --- | --- | --- | --- |
| **认得出**（识别） | 看到题能否联想到"这属于哪个情景" | **情景** | 点选"你会想到哪些方法" |
| **用得出**（执行） | 联想到了，手上能否真算对 | **方法** | 写关键步骤 / 做对 |

> 用户的痛点是**认不出**，不是**算不对**。
> 如果画像只按"方法"记，系统会误判"你洛必达掌握良好"——因为你确实会算，但根本没想到要用它。
> **这正是普通错题本治不了他的原因。**

**情景掌握度 = 召回完整度**（不是"会 / 不会"）：

> "看到 0/0 只想到洛必达" 与 "看到 0/0 能想到等价无穷小、洛必达、泰勒，
> 且知道优先用等价无穷小" —— 两者差别巨大，**后者才是"想出哪些解法"**。

### 1.8 掌握度机制（对外三档 / 内部四态）

**对外永远只有三档**（用户选定，不可增加）：

```
未接触 ──（问答里见过它解题）──→ 巩固中（内部标记"只见过，没自己做过"）
       ──（自己练过 / 答对过）──→ 巩固中
                                  │ 累计成功次数达标 + 跨不同题面
                                  ↓
                               已掌握
                                  │ 之后又做错 → 退回（内部标记"生疏"）
                                  ↓
                               巩固中
```

**内部状态机（四态）**：`未接触 → 暴露 → 巩固中 → 已掌握`

**升级条件（累计制，无任何时间限制）**：

1. **累计成功次数达标**：认出累计 3 次 / 用出累计 2 次
2. **跨不同题面**：认出须来自 ≥ 3 种不同题面；用出须 ≥ 2 道不同的题
   （不跨题面，测的是记忆，不是迁移）

**硬约束**：

- ❌ **不设任何时间条件**。不保证每天使用，任何"隔天 / 跨日期 / N 天未碰降级"都不公平。
  → **掌握度永不因时间流逝而降级**，只会因"做错"而改变。
  → **遗忘曲线在本体系里不成立。**
- ✅ **累计制**：错一次不倒退（出错不加分，不清零）。
- ✅ **已掌握后又做错** → 退回「巩固中」，累计成功数 **减一**（不归零）。
- ✅ **"暴露"不新增档位**：未接触 → 不在足迹树里出现（只在方法页反向链接里以最浅色出现）；
  暴露（碰过没练过）→ 显示为「巩固中」，用**最浅的深浅**表示。

### 1.9 三个互不打扰的区域

| 区 | 角色 | 作用 | 什么时候打开 |
| --- | --- | --- | --- |
| **问答** | 安静的解题台 | 贴题 → 解题；系统**静默采走原料** | 做题被卡住的当下 |
| **练习** | 训练场 | 用变式题检验"情景 → 方法"的识别与执行 | 有整块时间、想练、想验证时 |
| **足迹** | 地图 / 画像窗口 | 把"系统记住的你"摊开给你看 | 心里发虚时、考前规划时 |

**闭环**：问答产出原料 → 练习验证与改造 → 足迹呈现 → 你决定练什么 → 回到练习。

**唯一能改变掌握度的地方是练习**；问答只让你"见过"。

### 1.10 产品性格（硬约束，违反即做错）

1. **静默服务**：系统不主动提醒用户该做什么、不该做什么；只是在正常使用时尽力服务，**静默记录**。
   - 推论一：**永不主动推送 / 提醒 / 催办**
   - 推论二：**没有"定期"总结**，只有"你来看的时候，它给你一份新鲜的"
   - 推论三：练习 / 总结的**触发权完全在用户手上**
   - 一句话概括性格：**你不问，它不存在**
2. **后台重、前台轻**：AI 背后做很多活（拆解、归一、算掌握度、更新画像），
   但摆在用户面前的必须**很轻**，否则用户变成"在给系统打工"。
3. **淡**：不用百分比、不用勋章、不用红点、不做 KPI 面板。
4. **零彩色**：见 `02-功能文档.md` 视觉规范。
5. **只长碰过的**：前台地图只显示用户碰过的部分（连板块也只长碰过的）。

### 1.11 明确"不做"清单

| 不做 | 原因 |
| --- | --- |
| 账号系统 | 单人优先，本地存储 |
| 云同步 / 多端同步 | 手机 = 真身，电脑 = 开发台，本就不在同一设备 |
| 底部标签栏 | 改用顶部一行三标签（照搬 Grok 的排法） |
| 主动推送 / 提醒 / 定时复习 | 违反"静默服务" |
| 时间维度（遗忘曲线、周期巩固） | 违反"无任何时间限制"硬约束 |
| 问答界面里任何练习入口 | 问答必须绝对纯净 |
| AI 在对话里做任何**结构化标注**（标签 / 折叠条） | 见 1.12 与待定文档 |
| 难度爬坡 / 前置概念作为默认输出 | 用户明确未选 |

### 1.12 一处**已知的内部矛盾**（务必先看）

**"问答里 AI 到底吐不吐那一句定性？"** 需求笔记里有两处相互冲突的记录：

- 早期（洞 1 归位机制）：**前台自由生成一句话**（如"这题是 0/0 型，先用等价替换"），
  用户立刻看到；后台拿它当"板块提示"。
- 后期（前端形态第 14 节，用户三次否决后）：**AI 在对话里只解题，不做任何标注。**
  （用户原话否决项之一是"给每条回答头挂情景名标签——AI 一次性知道不了那么多，而且累赘"）

**当前执行口径**：以晚期的为准——**问答回答里不加任何结构化标注**（无标签、无折叠条）；
后台**自己判板块**（11 选 1~2）后再精匹配，不依赖前台句子。
**是否保留一句自然语言定性，见 `03-讨论遗漏与待定.md`，不要自行决定。**

### 1.13 术语表

| 术语 | 含义 |
| --- | --- |
| **板块** | 骨架第一层，如"极限""导数与微分"；共 11 个 |
| **情景组** | 板块下的分组层，共 42 个；仅为控制分支数 |
| **情景** | "看到什么"，如 0/0 型；识别单元 |
| **方法** | "想到什么"，如洛必达；执行单元 |
| **边** | 一条「情景 → 方法」的连线，是本产品可训练的最小单位 |
| **暴露** | 用户在问答里碰过某节点（内部状态，不新增对外档位） |
| **主线** | 一道题通常命中多条边；其中一条标为"主线"（首选定性的那条） |
| **处方** | 练习页的第一句："你这块最漏的是……先练这个" |
| **反向链接** | 方法页里的"这招还能用在这些地方"，即「方法 → 它能覆盖哪些情景」 |

## 2. 存在形式与技术选型

### 2.1 存在形式（已定案，不要改动方向）

**纯前端 + 本地存储**。后端逻辑**降级为前端可直接 import 的模块**，原因：

> 要出安卓 APK，就不能依赖"电脑上跑的 Node 后端"。
> → LLM **直连**（App 内走原生 HTTP 绕 CORS），存储走 **WASM SQLite + IndexedDB**。

### 2.2 一套代码，三端

**开发态 = 浏览器**（99% 的时间）。Electron / Capacitor 只是"打包壳"，**不是开发环境**。

```
frontend/                ← 唯一源码
   ↓ vite build
frontend/dist            ← 同一份产物
   ├── 浏览器直接打开      ← 开发与调试
   ├── Electron 壳        ← 桌面（可选，可后加）
   └── Capacitor 壳       ← 安卓 APK（主形态）
```

- 三层壳**互相独立、互不影响**，每层都可选、可后加。
- 日常开发**零额外环境**；只在验证"平台特有的东西"时才需要对应环境：
  - 桌面：文件对话框 / 本地路径
  - 安卓：相机权限 / 原生 HTTP / 触摸
- 安卓调试可选：`npx cap run android --livereload`，或 `chrome://devtools` 远程调试手机 WebView。

### 2.3 技术栈（建议，可微调但不要引入重型框架）

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 框架 | **React 18 + Vite** | 与参照项目一致 |
| 样式 | **Tailwind CSS** | 配合 CSS 变量做主题 |
| 状态 | **zustand** | 轻量，不引 Redux |
| 图标 | **lucide-react** | 线性图标，符合"极简"调性 |
| Markdown | **react-markdown** | 渲染 AI 回复 |
| 公式 | **KaTeX**（`react-katex` / `katex`） | **最硬的依赖，必须一开始就接** |
| 存储 | **sql.js**（SQLite → WASM）+ IndexedDB 持久化 | 单文件数据库，最好迁移 |
| HTTP | 浏览器 `fetch`；Capacitor 下走原生 HTTP 插件 | 绕开 CORS |
| 打包 | Electron（electron-builder / NSIS）；Capacitor（Android） | |
| CI | 云端 GitHub Actions 可出 APK | 可后加 |

## 3. 运行架构（前台 / 后台分离）

### 3.1 架构原则（用户提出，是全场最重要的一条）

> **前台同步只做一件事——解题；拆解、归位、画像更新全部下沉到后台异步队列。**

理由（用户原话）：分析记录和答疑是**异步的、完全解耦的**，晚几小时都无所谓，
多调用一次对用户完全没影响。

**它解锁了四件事**：

1. 两段式的延迟代价归零
2. 后台可失败重试，用户无感
3. 后台可用更贵更强的模型专做拆解
4. 可攒批一起做

**带来的开发顺序（重要减压）**：

- **第一阶段只做「问答」**——纯解题器，不接任何记忆，自己就能用
- **第二阶段再加后台拆解**——记忆系统整个后挂，**问答侧一行不改**

### 3.2 问答链路的落地

| 环节 | 做法 |
| --- | --- |
| 前台 | **1 次调用，同步，只解题**；答完立刻显示 |
| 后台队列 | 判板块（11 选 1~2）→ 该板块内精匹配到具体 id → 写库、更新足迹 |
| 失败 | 重试；实在不行**丢掉这条**（足迹少长一个节点，无伤） |
| 用户感受 | 全程无感 |

**命中多条边**：不做二选一，**全部记下，但标一个「主线」**。

**容错**：掌握度只由练习决定，所以归位错只会让足迹多 / 少长一个节点，**不会污染画像**。

### 3.3 AI 接入层（模型无关，硬要求）

**软件不绑定任何模型**——用户填哪个 API、放哪个模型就用哪个。
（产品负责人自己用 DeepSeek 4.1 flash，自带多模态 + 思考模式。）

由此推出三条约束：

1. **设置页必须能填**：API 地址（要求兼容 OpenAI 格式）+ API Key + 模型名 + 一个「支持图片」开关
2. **所有提示词不得依赖某个模型的专属能力**
   （不能写"请开启思考模式"这类话），只用通用的「指令 + 要求输出格式」，保证换模型不崩
3. **能力不足时优雅降级**：
   - 模型不支持图片 → 拍照 / 截图入口**变灰并说明原因**（而不是等报错）
   - Key / 地址填错 → 一个「**测试一下**」按钮当场告诉他
   - 模型数学弱 → 用户自己的选择，但设置页写明"建议用支持图片、数学能力强的模型"

### 3.4 调用次数与成本（第一阶段口径）

- **第一阶段：一次问答 = 1 次调用**（只解题）。
- 接记忆系统后，**后台**再加约 2 次（判板块 / 精匹配 / 画像更新），**异步、不影响等待**。
- 成本量级参考：**一题几分钱，一个月十几到几十块**（单价以各家官网为准，且有 prompt caching 可降）。
- 💡 **成本是用户自己的账**，软件不做任何成本估算、不加任何隐藏开销。

## 4. 数据模型

### 4.1 骨架数据（只读，随安装包发布）

骨架 = 系统内部的**全量知识网**，用户看不见全貌，但它是归位、处方、反向链接的基础。

- **全量骨架**：板块 → 情景组 → 情景 → 方法 的完整清单 + 方法之间的关系 + 题目来源
- **用户地图**：前台只显示用户碰过的部分
- **来源**：已由 LLM 生成 + 用户校对（基线为 `deepseek` 版），**不重跑**
- **形态**：**JSON 数据文件**，不占开发时间

**文件清单**（位于 `skeleton/`，打包进 `assets/skeleton/`）：

```
blocks.json                  # 11 个板块
scenario_groups.json         # 板块 → 情景组 映射（含 UI 规则与三份调整表）
scenarios.<blockId>.json     # 每个板块一个文件，如 scenarios.limit.json
methods.<blockId>.json       # 每个板块一个文件，如 methods.limit.json
meta.json                    # 元信息（范围、上下册划分）
```

**规模**：11 板块 / 42 情景组 / ~104 情景 / ~99 方法。
（`含参数极限` 已由"情景"降为**叠加标签**；一个情景组只有 1 个情景时界面跳过该层。）

### 4.2 用户数据表（建议 schema）

> 全部存于本地 **WASM SQLite**（经 IndexedDB 持久化）。
> 设计约束：**抽象出"学习者"实体、存储用可迁移格式、路径不写死**（为将来多人留后路）。

```sql
-- 学习者（单人环境下只有一行；为将来多人预留）
CREATE TABLE learner (
  id           TEXT PRIMARY KEY,
  display_name TEXT,
  created_at   TEXT NOT NULL
);

-- 设置（键值对：api_base / api_key / model / supports_image / theme …）
CREATE TABLE setting (
  key   TEXT PRIMARY KEY,
  value TEXT
);

-- 会话（一道题 = 一个独立会话；会话内可一直追问）
CREATE TABLE conversation (
  id           TEXT PRIMARY KEY,
  learner_id   TEXT NOT NULL,
  title        TEXT,                -- 取首条消息的题面缩写
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);

-- 消息
CREATE TABLE message (
  id              TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL,
  role            TEXT NOT NULL,    -- 'user' | 'assistant'
  content         TEXT NOT NULL,    -- Markdown + $公式$
  image_ref       TEXT,             -- 指向 image 表；无图则 NULL
  created_at      TEXT NOT NULL
);

-- 图片（拍照 / 截图）
CREATE TABLE image (
  id         TEXT PRIMARY KEY,
  blob       BLOB NOT NULL,         -- 或落盘路径，按平台决定
  created_at TEXT NOT NULL
);

-- 暴露记录：问答里"碰过"哪条边（由后台队列写入）
CREATE TABLE encounter (
  id             TEXT PRIMARY KEY,
  learner_id     TEXT NOT NULL,
  scenario_id    TEXT NOT NULL,
  method_id      TEXT,              -- 可空：只识别到情景、未识别到方法
  is_main        INTEGER NOT NULL DEFAULT 0,  -- 1 = 主线
  source         TEXT NOT NULL,     -- 'ask' | 'practice'
  occurred_at    TEXT NOT NULL
);

-- 掌握度（按维度分条记录）
CREATE TABLE mastery (
  id             TEXT PRIMARY KEY,
  learner_id     TEXT NOT NULL,
  target_type    TEXT NOT NULL,     -- 'scenario'（认得出） | 'method'（用得出）
  target_id      TEXT NOT NULL,
  state          TEXT NOT NULL,     -- 'exposed' | 'consolidating' | 'mastered'
  success_count  INTEGER NOT NULL DEFAULT 0,   -- 累计成功次数
  faces          TEXT NOT NULL DEFAULT '[]',   -- 已见过的不同题面指纹（JSON 数组）
  updated_at     TEXT NOT NULL,
  UNIQUE(learner_id, target_type, target_id)
);

-- 练习：一轮 = 同一条边、三道题
CREATE TABLE practice_run (
  id          TEXT PRIMARY KEY,
  learner_id  TEXT NOT NULL,
  scenario_id TEXT NOT NULL,        -- 本轮死磕的那条边所在情景
  method_ids  TEXT,                 -- 本轮涉及的方法（JSON 数组）
  started_at  TEXT NOT NULL,
  finished_at TEXT
);

CREATE TABLE practice_item (
  id          TEXT PRIMARY KEY,
  run_id      TEXT NOT NULL,
  seq         INTEGER NOT NULL,     -- 1 / 2 / 3
  step        INTEGER NOT NULL,     -- 出题难度梯度（1 换数字 / 2 换壳 / 3 换题面）
  question    TEXT NOT NULL,        -- JSON：题干、选项、正确答案
  answer      TEXT,                 -- JSON：用户作答
  result      TEXT,                 -- 'right' | 'wrong' | NULL
  created_at  TEXT NOT NULL
);

-- 后台拆解队列（异步、可重试）
CREATE TABLE queue_job (
  id              TEXT PRIMARY KEY,
  kind            TEXT NOT NULL,    -- 'locate' | 'update_mastery' …
  conversation_id TEXT,
  status          TEXT NOT NULL,    -- 'pending' | 'running' | 'done' | 'failed'
  attempts        INTEGER NOT NULL DEFAULT 0,
  payload         TEXT,
  created_at      TEXT NOT NULL
);
```

**迁移机制**：`migrations/vN_*.js` + `schema.sql`，与参照项目一致。

**导出 / 导入**：一个「**导出 / 导入一个文件**」的按钮，同时解决**备份 / 迁移 / 开发调试**三件事。
（不做云同步。这是"丢得起丢不起"的问题——数据全在手机本地，重装 App 就全丢。）

### 4.3 掌握度状态机（实现要点）

```
写库时机：
  1) 问答答完 → 后台 encounter(source='ask')
     → 若该(target)此前为「未接触」，置为 exposed（对外显示为"巩固中·最浅"）
  2) 练习判完 → 若答对：success_count += 1，加入题面指纹
     → 若满足升级条件，state 升为 'mastered'
     → 若答错且当前为 'mastered'：state 退回 'consolidating'，success_count -= 1
```

- **认出（scenario）**：累计 3 次成功 且 **≥ 3 种不同题面**
- **用出（method）**：累计 2 次成功 且 **≥ 2 道不同的题**
- **题面指纹**：建议对"题干归一化后的结构"（去掉具体数字、变量名）做哈希，
  用于判断"是不是同一个马甲"。
- **永不因时间降级**（不要写任何基于日期的逻辑）。

### 4.4 两个派生视图（纯前端计算，零 AI 成本）

**A. 足迹树**：过滤 `mastery` 中 state ≠ 'exposed' 的节点，按 板块 → 情景组 → 情景 → 方法 组装；
只保留用户碰过的分支（未接触的**完全不出现**）。

**B. 方法页反向链接**（Obsidian 式联系图谱的落点）：

- 数据来源：骨架里每个方法都带 `applies_to_scenarios`（该方法适用于哪些情景）——
  **关系早就记好了，只是从未反过来显示**。
- 实现：对 `方法 → 情景` 做一次**倒排索引**，纯前端、内存里算。
- **显示范围：全列**（包含用户还没碰过的情景）。
  理由：如果只显示碰过的，功能等于没有——"这招还能用在哪"的答案就是它自己，零信息量。
  **全部的价值就在"这招还能用在那些你还没去过的地方"。**
- **与"只长碰过的"不冲突**：

  | | 管什么 | 为什么 |
  | --- | --- | --- |
  | 只长碰过的 | **地图上的节点**（用户的领地） | 靠经历长出来 |
  | 反向链接 | **方法的固有属性** | "洛必达适用于 0/0 和 ∞/∞"是客观事实 |

- **筛选门槛**：只对 **跨 ≥ 2 个板块** 或 **适用情景 ≥ 4 个** 的方法显示
  （窄方法只有 2~3 个去处，显示出来显得空洞）。
- **呈现**：碰过的深、没碰过的最浅；**不加任何文字标记**（不写"你还有 4 个没去过"）。

## 6. 性能与兼容性红线

1. **`backdrop-filter`（毛玻璃）在低端安卓上很贵，且顶栏常驻重绘最耗**。
   → **毛玻璃只用两处：抽屉拉出时的遮罩 + 输入框**；**顶栏保持纯平**。
2. **动效**：`150~200ms`、`ease-out`、淡入 + 轻微位移；**不做弹跳、不做长动画**。
3. **公式必须用 KaTeX 渲染**；行内公式随正文，独立公式单独成块。
   （高数满屏分式 / 积分号 / 求和号，纯文本不可读。）
4. 长列表（足迹树可能上百节点）用**虚拟化或惰性展开**，避免一次性渲染全部节点。
5. 明暗跟随系统；不做主题切换开关（除非后续明确要求）。

| --- | --- | --- |

## 8. 附录：骨架数据字段清单

> 以下字段**全部是现成数据**，实现时不要重新设计，直接读。

### 8.1 `blocks.json`（数组）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 如 `B.limit` |
| `name` | string | 如"极限" |
| `aliases` | string[] | 别名 |
| `order` | number | 排序 |
| `chapter_ref` | string[] | 教材章节引用（如"同济第七版 上册 第一章"） |
| `summary` | string | 一句话概述 |
| `prerequisites` | string[] | 前置板块 id |
| `scenario_ids` | string[] | 本板块下的情景 id |

### 8.2 `scenario_groups.json`

- `meta`：含 `hard_limit`（每层分支 ≤ 7）、`ui_rule`（单情景组跳过该层）、`relation_rule`
- `blocks[]`：每项 `{ block_id, name, groups[] }`，
  每个 group = `{ id, name, order, scenario_ids[] }`
- 三份调整表：`added_scenarios`（补 2 个）、`id_normalization`（id 归一映射）、`methods_to_add`（补 5 个方法）

### 8.3 `scenarios.<blockId>.json`

包装结构 `{ "block_id": "B.xxx", "scenarios": [...] }`。每个情景：

| 字段 | 类型 | 说明 | UI 用途 |
| --- | --- | --- | --- |
| `id` | string | 如 `S.limit.0over0` | 主键 |
| `block_id` | string | 所属板块 | 建树 |
| `name` | string | 如"0/0 型未定式" | 足迹节点名 |
| `definition` | string | 一句话定义 | 方法页 / 详情 |
| `signals` | string[] | **触发信号**（怎么认出它） | **练习判题、方法页** |
| `recognition_examples` | string[] | 识别例题 | 详情展示 |
| `distinguish_from` | `{scenario_id, how}[]` | 与哪些情景易混、怎么区分 | 详情展示 |
| `methods` | `{method_id, priority, when_to_prefer}[]` | 本情景下的方法 | **足迹排序 + 选择线索** |

> ⭐ `when_to_prefer` = **"这个方法最适合什么情况"**，是骨架最有价值的字段。
> 例：「0/0 型 → 等价无穷小替换」写的是"分子分母由 sin、tan、ln(1+x)… 以乘除方式构成时首选"。
> **展开情景时，每个方法后面跟一句它自己的 `when_to_prefer`**（用户的拍板，见功能文档）。

### 8.4 `methods.<blockId>.json`

包装结构 `{ "block_id": "B.xxx", "methods": [...] }`。每个方法：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 如 `M.lhopital` |
| `name` | string | 如"洛必达法则" |
| `aliases` | string[] | 别名（含 id 归一后的旧 id） |
| `one_liner` | string | 一句话说明 |
| `block_ids` | string[] | 涉及板块 |
| `applies_to_scenarios` | string[] | **该方法适用于哪些情景** ← 反向链接的数据源 |
| `triggers` | string[] | 使用前兆 |
| `steps` | string[] | 操作步骤 |
| `preconditions` | string[] | 适用前提 |
| `not_applicable` | string[] | **什么时候不能用**（避坑） |
| `pitfalls` | string[] | 常见陷阱 |
| `relations` | `{type, target, note}[]` | `prefer` / `alternative` / `compose`，构成方法地图骨架 |
| `difficulty` | number | 难度 |
| `frequency` | string | `high` / … |
| `exam_notes` | string | 考试提示 |
| `example_problems` | `{statement, answer_sketch, scenario_id}[]` | 例题 |

### 8.5 `meta.json`

- `subject`（学科）、`scope`（教材范围）、
  `semester_split`（上册 6 板块 / 下册 5 板块）、`generated_at`
